1. Executive summary and product vision
CISGuard 360 is a centralized, GUI-backed, deterministic security configuration assessment and controlled 
hardening platform. It evaluates applicable CIS Benchmark requirements against live or explicitly labeled offline 
configurations for Windows, Linux, specified enterprise firewall vendors, and Cisco routers/switches. It generates 
verifiable findings and reports with remediation guidance, while offering advanced cross-layer risk analysis, 
constraint-aware planning, safety verification and evidence-backed post-change assurance.
Product principles
 Full source PS coverage is the baseline. None of M01-M38 may be removed to make space for extras.
 The complete 88-feature inventory is retained as planned scope; no feature is labeled complete without 
evidence.
 Deterministic means identical versioned inputs and rules yield identical auditable results. No runtime 
LLM/AI/ML is used.
 Read-only by default. Any hardening requires valid privileges, review, backup/prechecks, explicit approval 
and post-checks.
 Unknown, unavailable or unsupported evidence is never silently treated as a successful compliance check.
 Vendor and firmware compatibility is explicit; a generic adapter does not imply full support for every vendor 
variant.
Definition of system value
User question CISGuard 360 answer
What is wrong? Precisely identified control failures with vendor and benchmark versions.
Where and why? Actual evidence, affected assets, contextual risk scenarios, rule explanation.
What should change? Applicable CLI/API guidance, vetted alternatives and constrained plan.
Will it break a service? Model-supported what-if analysis + service-safety contracts and confidence/coverage.
Did it work? Re-audit + real connectivity/service checks; signed evidence-linked proof.
Will it stay fixed? Historical snapshots, scheduled reassessment, drift and alerts.
2. Problem, goals, users and use cases
Problem
Organizations operate heterogeneous Windows/Linux endpoints and servers, firewalls, routers and switches. 
Manual CIS auditing is inconsistent and slow. Device-specific configuration formats, benchmark revisions, 
privileged access and multi-device operational dependencies make assessment, safe correction and evidence 
collection difficult.
Product goals
 G1. Assess all specified platform families and applicable security control categories from one management 
experience.
 G2. Maintain versioned, customizable, explainable compliance policy packs.
 G3. Present actionable, exportable and auditable results by asset type, risk/severity and control.
 G4. Connect related misconfigurations into evidence-backed cross-device risk scenarios.
 G5. Minimize hardening disruption via constraint-aware planning and simulation where supported.
 G6. Provide approval-gated remediation, meaningful verification, evidence integrity and ongoing monitoring.

Status and scoring rules
Status Meaning / treatment
PASS Applicable automated control was assessed and met expected condition.
FAIL Applicable automated control assessed and did not meet expected condition.
NOT_APPLICABLE Control irrelevant for asset or agreed context; excluded from denominator.
MANUAL_REVIEW Additional human evidence needed; excluded from assessed denominator until validated.
ERROR Attempted assessment failed; never counted as pass.
NOT_ASSESSED No attempt or missing support/evidence; never counted as pass.
EXCEPTION Policy-approved time-bound exception; retains original technical finding and is reported separately.
SCORING INVARIANT  Assessed compliance = PASS / (PASS + FAIL) x 100 for applicable automated checks; show 
assessment coverage alongside every score. Severity-weighted organizational scores may supplement, never 
overwrite, this measure.

7. Collector, normalization and policy engine specification
7.1 Device adapter contract
Each adapter implements: probe_version(), collect(read_only=True), parse(), normalize(), supported_controls(), 
validate_credentials(), get_remediation_capabilities(), and an optional execute_approved_change(). Adapters must 
explicitly enumerate unsupported versions/capabilities and ensure read-only probes do not modify state.
Normalized object Required fields
Asset asset_id, org_id, family, vendor, model, os/firmware_version, collector_version
Management interfaces, enabled protocols, auth settings, timeout and exposed subnet metadata
Network policy rules, order, zones, address/service objects, source, destination, action, NAT where known
OS security facts users/groups, service states, auth/audit policies, firewall and file/registry configuration
Topology interfaces, links, subnets, routes, VLANs, trusted/untrusted scope

7.2 Sample rule schema (conceptual)
id: org-ssh-telnet-001
source: organizational-override
applies_to: [cisco_ios]
when:
  fact: management.telnet_enabled
  operator: equals
  value: true
expected:
  management.telnet_enabled: false
severity: high
remediation_template: cisco_ios_vty_ssh_only
requires_manual_review: false
This is an illustrative organizational override, not a claim of exact official CIS control wording. Official rule IDs and 
requirements must be bound to an authorized benchmark release and reviewed.
7.3 Deterministic rule execution
 Validate pack schema and signature; resolve platform, benchmark edition/profile, organization overrides and 
exceptions.
 Evaluate applicability separately from pass/fail; missing evidence produces ERROR or NOT_ASSESSED.
 Run allowlisted operators: equals, contains, regex with limits, range, set membership, CIDR containment, 
ordered ACL semantics, optional XCCDF/OVAL evaluation.
 Persist expected, actual, raw evidence reference, normalized fact, evaluator version, confidence/coverage 
limitations and remediation pointer.
 Produce scoring and export records from one canonical results store, never from separate front-end 
calculations.
7.4 Benchmark rights and mappings
CIS benchmark contents are subject to terms. Do not redistribute proprietary benchmark text or machine-readable 
packs without rights. Store source attribution, version, profile, control mapping and rights metadata. 
Organizational-authored rules must be labeled separately from official benchmark checks. 
OpenSCAP/ComplianceAsCode content must not be misrepresented as a complete CIS benchmark mapping without 
validation.

8. Security intelligence, optimization and simulation
8.1 Cross-layer evidence graph
Graph nodes represent assets, interfaces, networks, routes, services, policies, security controls and findings. Typed, 
evidence-linked edges encode hosted-on, attached-to, routes-to, allows/denies, depends-on and violates. Evidence 
quality and topology completeness are explicit attributes.
8.2 Risk correlation
Author deterministic scenario definitions: required predicates, source-finding IDs, reachable path conditions, 
exclusions and confidence/unknown handling. The system must not assert a validated attack path solely from 
textual similarity of two findings.
8.3 Minimal-change remediation planner
Use a vetted catalog of vendor/version-specific candidate actions. OR-Tools CP-SAT selects actions to satisfy security 
targets while minimizing weighted disruption/change cost subject to immutable service-safety and access-
management constraints. If no feasible plan exists, return UNSAT with violated constraints; do not fabricate a 
recommendation.
Constraint type Example
Security Eliminate prohibited public SSH access under effective policy.
Availability Preserve admin subnet to managed device access path.
Dependencies Apply route/ACL updates in an order that avoids lockout.
Capability Do not choose API action unsupported by running firmware.
Approval Execution needs approver + operator separation for critical operations.
Recovery Prohibit automatic action without verified recoverability where policy requires it.
8.4 What-if model and confidence
Construct baseline and candidate snapshots. Analyze supported routing, ACL, NAT and host/network policy 
behavior, then test service-safety contracts. Prediction output: SAFE_IN_MODEL, VIOLATES_CONTRACT, 
UNSUPPORTED, or INSUFFICIENT_EVIDENCE; never present model prediction as universal proof of operational 
safety.
8.5 Modeling gaps
Batfish is the initial supported-vendor modeling engine; custom semantics adapters are required for unsupported 
platforms or behaviors. For unsupported cases, design conservative prechecks, staged change rollout and 
measured post-change tests. Unknown model coverage should block fully autonomous hardening whenever a 
mandatory contract depends on it.
9. Controlled hardening, verification and proof
9.1 State machine
DRAFT -> SIMULATED -> PRECHECKED -> PENDING_APPROVAL -> APPROVED -> EXECUTING -> VERIFYING -> 
VERIFIED / FAILED / ROLLED_BACK / NEEDS_MANUAL_RECOVERY. Terminal states are immutable audit events. 
Reattempts create linked executions rather than overwriting evidence.
9.2 Safety gates
 Scope authorization and exact device identity/version verified.
 Credentials retrieved only by eligible worker through OpenBao; no logs of secrets.

9.3 Verification requirements

cannot be reversed must be identified ahead of time with manual recovery requirements.

Produce an evidence dossier referencing original failure, source artifact hash, benchmark release, approved 
change plan, simulation contract outputs, operator/approver identities, execution log, new configuration hash, re-
audit outcomes, post-service tests, residual risk and cryptographic signature/integrity manifest.

10. Product security and privacy
Security requirements
ID Control Requirement
SEC-01 Tenant isolation RLS for client-accessible data and tenant-aware backend enforcement on all routes and worker tasks.
SEC-02 Authentication Supabase Auth; MFA for privileged roles; validate JWT issuer, audience, signature, expiration.
SEC-03 Authorization Granular permissions: view, scan, policy edit, approve, remediate, export and admin.
SEC-04 Secrets OpenBao for privileged device keys/tokens; zero plaintext in DB, logs, reports, crash dumps.
SEC-05 Transport TLS to backend and vendors; SSH host key checking; reject unsafe verification bypass by default.
SEC-06 Collection Read-only by default, least privilege, explicit scope and tenant ownership.
SEC-07 Evidence Encrypt sensitive artifacts, hash, sign manifests and restrict access/retention.
SEC-08 Execution Allowlisted commands/APIs, change approvals, independent pre/post checks, full activity record.
SEC-09 Software supply chain Pinned dependencies, CI secret scanning, SAST, container scanning and patches.
SEC-10 Availability Worker isolation, retry with idempotency, task timeouts and recoverable queue state.
SEC-11 Privacy Data minimization, retention controls, no sensitive config sent to external LLMs.
SEC-12 Audit integrity Evidence signature validation and restricted append-only event access.
Threats to consider
 Compromised operator account triggers unauthorized device change. Mitigation: MFA, RBAC, separation of 
duties and mandatory approval.
 Malicious configuration content exploits parser. Mitigation: input limits, safe parsing, sandboxed/scoped 
workers and no eval().
 Cross-tenant evidence leakage through object URLs. Mitigation: private storage, scoped signed URLs and 
backend checks.
 Secret exposure in configuration snapshots and CLI logs. Mitigation: encrypted storage, redaction, limited 
retention.
 Network lockout after remediation. Mitigation: precheck, access-preserving contracts, staged rollout and 
verified recoverability.
 Discrepancy between modeled and real behavior. Mitigation: capability bounds, real post-change service 
checks and explicit unsupported states.

13.2 Per-feature done criteria
 A feature has a versioned specification, owner, test cases, and correct real output for each declared supported 
configuration.
 Collector or engine behavior is verified on fixtures and authorized OS/device lab conditions when applicable.
 Known failure/unknown/unsupported paths are tested, documented and visible in the GUI and exports.
 Security threat and privilege impact reviewed; no credentials or sensitive config leak.
 Evidence (logs, snapshots, screenshots, test output) attached and linked to the stable feature ID.
 No feature is marked complete merely because a UI control exists or a library was installed.

platform-specific acceptance tests, appropriate security testing, and report/evidence reconciliation. Hardware or 
vendor firmware not tested must be explicitly disclosed as unverified.
